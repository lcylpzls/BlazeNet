# BlazeNet 数据存储设计文档

> 状态：v1.0（待人工审核）
> 日期：2026-08-26
> 依据：05-系统架构设计文档

## 1. 存储总览

| 数据 | 存储位置 | 技术 |
| --- | --- | --- |
| 调度中心业务数据 | 调度中心 | redb 4.2（单文件，ACID） |
| 游戏版本元数据 | 原始节点/IDC | 每版本一个 `.gameindex` |
| 内容块 | 原始节点/IDC | 每游戏一个 `blocks.pack` |
| 网吧真实文件 | 网吧服务器 | 普通文件系统目录 |
| 网吧临时块 | 网吧服务器 | 临时目录（24h 生命周期） |
| 热榜/peer 列表 | 调度中心内存 | 进程内缓存，redb 落底 |

不使用 Redis；不使用数据库做内容块存储。

## 2. 调度中心 redb 表设计

约定：所有表均为 key-value；主键即 key；关联表以复合 key 表达关系；时间字段统一 i64 毫秒时间戳；ID 统一 u64（自增由调度中心分配）。

### 2.1 users（账号）

| key | value |
| --- | --- |
| `users/{id}` | `{id, username, password_hash, salt, created_at}` |

### 2.2 places（场所/网吧）

| key | value |
| --- | --- |
| `places/{id}` | `{id, name, region, remark, created_at}` |

### 2.3 groups（分组）

| key | value |
| --- | --- |
| `groups/{id}` | `{id, name, remark}` |

### 2.4 绑定表（多对多）

| 表 | key | value |
| --- | --- | --- |
| 用户-场所 | `bind_user_place/{user_id}/{place_id}` | `{created_at}` |
| 用户-分组 | `bind_user_group/{user_id}/{group_id}` | `{created_at}` |
| 分组-场所 | `bind_group_place/{group_id}/{place_id}` | `{created_at}` |

> 查询某用户可管理的全部场所 = 直绑并集 + 所属分组绑定的场所并集。一期不建冗余反查表，规模上来再评估。

### 2.5 nodes（节点）

| key | value |
| --- | --- |
| `nodes/{id}` | `{id, node_type: origin/idc/cafe, name, place_id, endpoint_id, status, heartbeat_at, offline_count, config: {concurrent_games, disk_threshold, chunk_concurrency, ...}, created_at}` |
| `nodes/{id}/addrs` | `{addrs: [{addr, kind: config/stun/manual, link_label, status, ping_fail_count, last_pong_at}]}` |

### 2.6 games（游戏）

| key | value |
| --- | --- |
| `games/{id}` | `{id, name, producer, status: uploading/published/maintenance, current_version, latest_version, heat, updated_at}` |
| `games/{id}/versions/{version}` | `{version, manifest_path, chunk_count, total_bytes, published_at, status}` |

### 2.7 块账本

| key | value |
| --- | --- |
| `game_chunks/{game_id}/{chunk_hash}` | `{holders: [node_id,...], version_refs: [version,...]}` |
| `node_chunks/{node_id}/{game_id}/{chunk_hash}` | `{size, updated_at}` |

> 块账本以"游戏维度"管理（每游戏一套索引，与 pack 对应）；心跳对账用节点侧摘要（版本数、块数、占用）比对。

### 2.8 tasks（任务）

| key | value |
| --- | --- |
| `tasks/{id}` | `{id, game_id, version, node_id, place_id, kind: download/update/rollback, status: queued/downloading/merging/ready/failed/cancelled, assign_chunks, progress, retry_count, error, created_at, updated_at}` |
| `tasks/{node_id}/queue` | `队列顺序（调度中心内存 + 落底）` |

### 2.9 heat（热度）

| key | value |
| --- | --- |
| `heat/{game_id}` | `{launch_count, updated_at}` |

### 2.10 audit_logs（审计）

| key | value |
| --- | --- |
| `audit/{seq}` | `{user_id, action, target_type, target_id, detail, ip, created_at}` |

### 2.11 config（系统配置）

| key | value |
| --- | --- |
| `config/{key}` | 全局参数（保活周期、失败阈值、默认并发等，均可覆盖为节点级配置） |

## 3. `.gameindex` 版本清单格式（二进制）

每版本一个文件，建议路径：`<游戏ID>/index/<version>.gameindex`。

```text
magic "BLZGI" (5B) | format_version u16 | flags u16
file_count u32
repeat file_count:
    file_name_len u16 | file_name bytes | file_hash[32] | chunk_count u32
    repeat chunk_count:
        chunk_hash[32] | chunk_len u32
manifest_hash[32]（整文件 BLAKE3，覆盖上述全部内容）
```

- 固定小端序；校验：整文件 BLAKE3 附在文件尾（32B）；
- 清单不包含 pack 偏移：各节点 pack 布局不同，块在 pack 中的位置由**节点本地索引**记录；
- 文件级 `file_hash`：网吧合并后校验依据；
- 同一哈希在多文件/多版本出现 = 只存一份，索引重复引用。

## 3.1 索引职责区分

| 索引 | 生成方 | 存放位置 | 用途 |
| --- | --- | --- | --- |
| 内容索引（`.gameindex`） | 制作机 | 原始节点/IDC/网吧服务器 | 版本语义：文件→块序列、file_hash、块哈希/长度；IDC 用于计算缺失块，网吧用于文件级对账与合并 |
| 本地块索引 | 节点本地 | 仅原始节点/IDC | `chunk_hash → (pack 偏移, 长度)`，只用于定位和提供块数据 |

- 内容索引**不包含 pack 偏移**，是纯内容语义，可跨节点共享；
- 网吧服务器不建本地块索引：真实文件的块位置由旧版 `.gameindex` 文件内块序列推导（按序累计偏移），临时块按目录扫描；
- 两个索引职责分离，禁止混用。

## 3.2 更新计划（UpdatePlan）

由 `blaze-common` 提供纯逻辑（对比新旧 `.gameindex`），制作机与网吧 agent 复用。

输入：

- 新版本 `.gameindex`；
- 旧版本 `.gameindex`（网吧本地已就绪版本）；
- 临时块目录清单（下载中断/取消后保留的块）。

输出（四类）：

1. `files_to_download`：新索引有、旧索引没有的文件（新文件，全部块需下载）；
2. `files_to_update`：两边同名且 `file_hash` 不同的文件（内容变化，只需下载缺失块）；
3. `files_to_delete`：旧索引有、新索引没有的文件（合并完成后删除）；
4. `chunks_to_download`：需要下载的块列表（全局去重）= 新索引全部唯一块 − 旧索引全部块 − 临时块已有块。

规则：

- 变化文件判定以 `file_hash` 为准（FastCDC 确定性：内容相同则块序列相同）；
- 块来源优先级：临时块 → 旧索引块（合并前从真实文件偏移读）→ 下载；
- 删除文件在合并完成前不删除，其块仍可作为其他文件的块源；
- 同一块被多文件引用只下载一次；
- 执行顺序：①下载全部缺失块到临时目录 → ②按文件重组合并（未变化块从旧文件偏移读、新块从临时目录读，校验 file_hash 后原子替换）→ ③删除 `files_to_delete` → ④临时块按 24h 规则清理；
- 文件重命名（内容相同、文件名不同）一期不识别，按"删旧 + 下载新"处理，内容级复用留二期评估。

## 4. `blocks.pack` 块大文件格式

```text
magic "BLZPK" (5B) | header_len u32 | 版本/参数头（保留）
... 追加写入的块数据（每块：无头，位置由索引记录）...
```

规则：

- 只追加，不原地修改；新块 append 到文件尾；
- 块位置由节点本地索引记录（`chunk_hash → (pack_offset, pack_len)`，存于节点本地 redb，首次同步或启动时构建）；
- 垃圾块 = 不被"当前版本 + 上一版本"引用的块；
- 压缩：垃圾占比 ≥ 节点配置阈值（默认 30%）且可用空间 ≥ 存活字节数时，整文件重写为 `blocks.pack.compact`，成功后原子改名；
- 压缩期间新块写入新文件；失败/中断保留旧文件，残留垃圾可下次压缩回收；
- 单游戏一个文件，不跨游戏共享。

## 5. 网吧服务器目录布局（默认方案）

```text
D:\BlazeGames\
  <game_id>\
    index\<version>.gameindex        # 每版本索引
    files\...                         # 真实游戏文件（原始目录结构）
  .blaze\
    temp-chunks\<game_id>\<chunk_hash>.blk   # 下载中/未合并差异块
    serve-index\...                   # 块 → 真实文件(路径,偏移,长度) 映射（redb 本地）
  logs\
```

合并规则：

- 合并文件写入同目录、同文件名 + `.new` 扩展名；
- 文件哈希校验通过 → 删除旧文件 → 改名原子替换；
- 校验失败 → 删除 `.new`，保留旧文件，重试，多次失败告警；
- 临时块保留 24 小时（自写入起），期间作为上传源；到期删除；之后请求从真实文件偏移读取。

## 6. 缓存与一致性策略

| 缓存 | 内容 | 策略 |
| --- | --- | --- |
| 内存热榜 | 游戏热度排序 | 每 10 分钟重算；崩溃后由 redb `heat` 重建 |
| peer 列表 | 节点地址（含多 IP） | 心跳/保活事件驱动失效；调度中心单实例无一致性问题 |
| 本地块映射 | 哈希→(文件,偏移,长度) | 网吧侧 redb 持久化；合并/删除时同步更新 |

一致性：

- 调度中心数据以 redb 事务为准，单实例无分布式一致性问题；
- 节点与调度中心对账 = 心跳摘要比对，不一致重新下发任务；
- 块内容不可变（内容寻址），索引可随时重建，因此块库不备份。

## 7. 备份

- 每日备份调度中心 redb 快照 + 配置文件（保留 7 天）；
- 块库不备份（可从制作机重传重建）；
- 网吧真实文件不备份。

## 8. 索引与约束

- redb 无需额外建索引，按 key 前缀访问（`bind_user_place/{user_id}/` 即用户绑定的场所集合）；
- 唯一性由 key 保证（如绑定表天然去重）；
- 禁止冗余字段：块账本不存块内容、节点表不存游戏清单（清单在任务/账本中推导）。
