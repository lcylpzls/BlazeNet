# BlazeNet 网吧游戏 P2P 分发系统 项目立项说明书

> 状态：初审版 v1.0（待人工审核）
> 日期：2026-08-26
> 依据：00-AI辅助软件开发全流程标准化手册 阶段1

## 1. 项目背景

网吧场景下，游戏客户端体积大（平均约 50GB、最大 200GB）、版本更新频繁（每周 5~10 款、单次更新 1~20GB）。传统"中心服务器逐台下发"模式存在三个问题：

1. 中心出口带宽成本高：同一份内容要传给每台 IDC/网吧；
2. 全量更新浪费带宽：版本间大部分文件内容相同，却重复传输；
3. 网络环境复杂：网吧处于 NAT 后，直连与上传能力受运营商限制。

本项目以"内容寻址分块 + P2P 互传 + 增量更新"为核心，构建一套面向网吧场景的分发系统。

## 2. 业务价值

- 中心出口带宽从"全量 × 节点数"降为"全量 × 1（按块分片下发，节点间互拉）"；
- 增量更新只传输版本间差异块，实测合成样本差异率 6.67%（avg 1MiB 参数），显著降低更新流量；
- 网吧服务器加入 P2P 上传，分摊 IDC 压力（打洞/端口映射可达时）。

## 3. 核心目标（一期）

1. 搭建"制作机 → 原始节点 → IDC → 网吧服务器"的块级分发链路；
2. 实现基于 FastCDC + BLAKE3 的增量更新与去重（跨版本共享块）；
3. 实现多源并行下载（块唯一分配、失败回填、RTT 就近排序）；
4. 实现 Web 管理后台（人工选择游戏下载、节点/任务/游戏管理）；
5. 完成 PoC 已验证的全部关键机制落地（含 relay 只打洞不传数据的路径门控）。

## 4. 非目标（一期明确不做）

- 客户机端一切功能（无盘工作站开机网络挂盘，客户机出界）；
- 网吧侧自动推送（仅人工选择下载）；
- 带宽时段限速（二期做"不上传降速下载"）；
- 动态抢占、预热拉块（二期）；
- IPNI/storetheindex 接入（暂缓）；
- Redis、容器化、Prometheus/Grafana（二期或不采用）；
- RBAC 角色权限（二期）、远程自升级（二期）；
- 自动淘汰低热度游戏（一期不做）。

## 5. 适用范围

- 一期部署形态：原始节点 ×1（Linux，仅服务 IDC）、IDC 节点 10~30（Linux）、网吧服务器 1000~3000（Windows）、调度中心单实例（与原始节点同机房）、relay 每机房一个独立服务；
- 全库 50~100TB，单游戏平均 50GB、最大 200GB；
- 内容类型：游戏安装包/更新包（二进制文件为主）。

## 6. 技术约束

- Rust 2024 edition，单代码库，tokio 统一运行时；
- 数据面：iroh 1.0.3（QUIC + NAT 打洞 + relay），自定义 ALPN 协议；
- 控制面：tonic 0.14 gRPC（长连接推送），prost 0.14；
- 调度持久化：redb 4.2（一期不用 Redis）；
- 分块：fastcdc 5.0（v2020），参数 min 64KiB / avg 1MiB / max 4MiB，块级 zstd 压缩；
- 内容寻址：blake3 1.8；
- 原始节点/IDC 块库：每游戏一个 pack 大文件 + 每版本 `.gameindex`；
- 任何期不容器化（需用 io_uring 等底层能力），二进制 + systemd/Windows 服务部署；
- NAT 网关限制：打洞端口必须使用 10001-65535；
- relay 只做打洞协助，不承载块数据（应用层路径门控强制）；
- 所有非功能性文本（注释、错误信息、打印、日志、界面文案等）一律使用简体中文；技术术语保持原名。

## 6.1 编译交付规范

- 所有编译交付物统一放置到 `bin/` 目录，按平台分 `bin/linux/` 与 `bin/windows/`；
- 制作机、网吧服务器程序：仅 Windows，交付到 `bin/windows/`；
- 原始节点、IDC 节点、调度中心、relay 等服务器组件：仅 Linux，交付到 `bin/linux/`；
- 编译时严格遵守该规范。

## 6.2 配置规范（仅限本项目）

- Linux 可执行文件：有且仅有一个参数 `--config <路径>` 指定配置文件，其余所有配置项均从配置文件读取；
- Windows 可执行文件：自动加载"程序目录上一级目录下的 `config/` 目录"中的配置文件，配置文件名固定并写死在代码中（制作机 `producer.toml`、网吧 agent `cafe-agent.toml`）；
- 配置文件统一使用 TOML 格式。

## 6.3 质量与 CI/Release 约束

- 单元测试覆盖率必须 100% 且全部通过（全绿），统计工具使用 `cargo-llvm-cov`；
- 配置 GitHub Actions 工作流：
  - CI：`cargo fmt --check`、`cargo clippy -D warnings`、`cargo test --all-targets`、覆盖率 100% 门禁；
  - Release：打 tag 触发，构建 `bin/linux/` 与 `bin/windows/` 交付物并上传 artifacts；
  - CI 与 Release 未全绿不得合并、不得发布。

## 7. 风险点

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| iroh 在真实 NAT 下打洞成功率不足 | 网吧上传能力受限 | 已确认降级策略：打洞失败只下载不上传；IDC 端口映射直连兜底 |
| relay 默认会转发数据，与"只打洞"约束冲突 | 违反网络预算 | 应用层 `paths()` 路径门控，PoC 已在真实 NAT 验证 |
| 带宽预算低 | 分发速度慢 | 1MiB 分块 + 块级压缩 + 多源并行 + 每块只从中心下发一次 |
| 调度中心一期单实例 | 宕机期间新任务暂停 | 存量内容不受影响，每日备份，二期 openraft HA |
| Windows 构建 iroh | 构建复杂度 | 需 cmake+nasm；打包 Windows 服务自启 |
| 单游戏块大文件损坏 | 该游戏不可用 | 可从制作机重传重建；块库不备份 |

## 8. 预期收益

- 中心出口流量约等于发布内容一份（不计重试）；
- 更新下载量约等于版本差异量（合成样本 6.67%，真实样本待实施期复测）；
- 网吧服务器可复用已下载内容作为上传源，分摊 IDC 压力。

## 9. 项目边界声明

本系统只负责"内容从制作机到网吧服务器磁盘"的分发管理；网吧无盘系统如何把文件提供给客户机不属于本项目范围。
