# BlazeNet 系统架构设计文档

> 状态：v1.0（待人工审核）
> 日期：2026-08-26
> 依据：03-项目PRD、04-开发计划、PoC 验证结果

## 1. 整体架构

```text
┌────────────┐   gRPC 上传   ┌──────────────────┐
│  制作机 CLI │ ────────────▶ │  原始节点（Linux） │
└────────────┘               │ 块库+数据面+上传  │
                             └───────┬──────────┘
                                     │ 块级分发（每块只下发一次）
                            ┌────────▼─────────┐
                            │  IDC 节点 ×N（Linux）│◀──┐ 块互拉
                            └────────┬─────────┘    │
                                     │ 只从 IDC/网吧拉 │
                            ┌────────▼─────────┐    │
                            │ 网吧服务器 ×M（Windows）│───┘
                            └──────────────────┘

┌───────────────────── 控制面（gRPC 长连接）─────────────────────┐
│  调度中心（单实例，与原始节点同机房） + Web 后台                  │
│  redb 持久化 / 块账本 / 任务推送 / 心跳 / 保活 / 热度 / 审计     │
└────────────────────────────────────────────────────────────┘

relay 服务（每机房一个，独立进程）：只打洞协助，不承载块数据
```

## 2. 分层设计

### 2.1 接入/控制面层

- 调度中心 gRPC 服务：节点注册、心跳、任务流（服务端推送）、块账本查询/上报、秒传查重、版本清单；
- 长连接 + 断线重连全量对账；
- 轻量 UDP 保活探针（25 秒一轮、窗口均摊、连续 3 次失败剔除）；
- Web 后台（HTTP）：账号/场所/分组、节点、游戏、任务、状态。

### 2.2 业务层

- 调度器：纳管计划、任务分片（不同 IDC 拉不同块）、多源分配（全局去重、唯一分配、失败回填、RTT 排序）、热度计算；
- 版本管理：上传中保护、commit 校验、版本级发布、回滚；
- 更新引擎（节点侧）：统一"拉索引→对账→清理→补缺→合并"流程；
- 块服务（节点侧）：批量流式响应、relay-only 路径门控、24h 临时块、真实文件偏移读。

### 2.3 数据层

- 调度中心：redb（账号/绑定/节点/游戏/版本/块账本/任务/热度/审计/配置）+ 内存缓存（热榜、peer 列表）；
- 原始/IDC：每游戏一个 `blocks.pack` + 每版本 `.gameindex`；
- 网吧：真实文件目录 + 临时块目录；
- 不做 Redis；块库不备份，调度中心数据每日备份。

## 3. 模块拆分（代码结构）

单代码库（Rust 2024 workspace），按可执行程序划分：

| 程序 | 平台（交付目录） | 模块 |
| --- | --- | --- |
| `producer` | Windows（`bin/windows/`） | 分块、差异计算、版本清单、gRPC 上传客户端 |
| `origin` | Linux（`bin/linux/`） | 上传服务、块库、commit 发布、数据面块服务 |
| `scheduler` | Linux（`bin/linux/`） | 控制面、块账本、任务调度、保活、后台 API、审计 |
| `web` | Linux（`bin/linux/`） | 后台前端（React + TypeScript + Vite + Ant Design 5，静态资源由 scheduler 托管） |
| `agent` | IDC 节点 Linux（`bin/linux/`）、网吧服务器 Windows（`bin/windows/`） | 注册、任务订阅、块库（IDC）、更新引擎、块服务 |
| `relay` | Linux（`bin/linux/`） | iroh-relay 独立服务（打洞协助） |

共享 crate：`blaze-common`（协议、类型、块库、FastCDC、更新计划 UpdatePlan、错误码）。

## 4. 流量模型

### 4.1 发布流量

- 制作机 → 原始节点：只传差异块（秒传跳过已有块），gRPC 双向流；
- 中心出口 ≈ 发布内容一份（不计重试），不随 IDC 数量翻倍。

### 4.2 分发流量

- 原始节点 → IDC：每块一次，按责任分片；
- IDC ↔ IDC：块互拉，优先其他 IDC；
- 网吧 ← IDC/网吧：RTT 就近优先；打洞失败只下载。

### 4.3 控制流量

- 1 万节点 × 心跳 25s ≈ 400 QPS（长连接消息）；
- 保活 ping：地址总数/25 ≈ 1600 pps（1 万节点 × 4 地址场景）；
- 与数据面相比可忽略。

## 5. 容错与降级

| 场景 | 策略 |
| --- | --- |
| 调度中心宕机 | 存量内容继续服务（peer 列表缓存）；恢复后心跳对账补任务 |
| 节点离线 | 责任块重新分配；离线期间不作为 peer 下发 |
| relay 不可用 | 该区域打洞协助失效；网吧降级只下载；不阻塞 IDC |
| 网吧打洞失败 | 只下载不上传；缺失块从 IDC 补 |
| 块下载失败 | 3 次退避重试 → 换源 → 回填全局缺失集合 |
| 任务失败 | 状态置失败，人工重发 |
| 磁盘满 | IDC/网吧停止纳管（可强制覆盖）；原始节点拒绝上传并告警 |
| 合并失败 | 保留旧文件、删 `.new`、重试、告警 |
| 版本上传中 | 临时禁止该游戏请求，取消进行中任务 |

## 6. 扩容方案

- IDC 节点：线性增加，天然扩容（块账本自动感知）；
- 网吧节点：数量线性增加，控制面按长连接 + 均摊保活设计（1 万节点有余量）；
- relay：每机房一个，按机房数量线性扩展；
- 原始节点：一期单点；如发布带宽不足，二期评估多原始节点/分片；
- 调度中心：一期单实例 + 每日备份；二期 openraft 三节点跨机房。

## 7. 安全约束

- 控制面：Token + TLS（内部 CA）；后台账号密码 + 会话；
- 数据面：iroh NodeId 身份认证；未注册节点不下发 peer 列表；
- 内容明文存储（QUIC/TLS 已加密传输，内容非机密）；
- relay 只打洞不传数据由应用层强制：`Connection::paths()` 检测，relay-only 连接拒绝块传输；
- 审计日志记录关键后台操作。

## 8. 关键设计决策记录

| 决策 | 原因 |
| --- | --- |
| iroh 1.0 + 自研 ALPN，不用 iroh-blobs | iroh-blobs 官方标注非生产质量；增量更新需要自定义块语义 |
| 每游戏单 pack 大文件 | 节省文件句柄、顺序读写；压缩按整文件重写（阈值/空间可配置） |
| redb 替代 RocksDB | 纯 Rust、ACID、无 C++ 构建链；单实例够用 |
| 不用 Redis | 单实例 + 内存 + redb 已满足；少一个运维组件 |
| relay-only 路径门控 | iroh 1.0.3 无 ForceDirect，默认 relay 会转发数据；应用层强制"只打洞" |
| 打洞端口 10001-65535 | NAT 网关限制 ≤10000 不可打洞 |
