# BlazeNet 三期迭代计划：性能优化

> 状态：进行中（P3.1/P3.2a/P3.4a/P3.5a/P3.6a 已完成，见
> [14-三期性能基准报告.md](14-三期性能基准报告.md) 与
> [15-三期落地与压测报告.md](15-三期落地与压测报告.md)）
> 日期：2026-08-27
> 目标：在不容器化的前提下，把数据面、磁盘 IO、控制面与前端做到万级节点、50GB 级游戏、200GB 单游戏的性能底座。

## 1. 三期总目标

1. 单节点数据面吞吐达到专用带宽 90% 以上（一期实测 LAN 约 7MB/s，瓶颈在 iroh/逐块 RPC，而非磁盘）；
2. 原始节点/IDC 磁盘 IO 从"每块一次 read/write + redb 事务"升级为异步批处理与零拷贝；
3. 引入 io_uring / IOCP 统一抽象，Windows 与 Linux 共用一套高性能 IO 代码路径；
4. 调度中心支撑 1 万节点、每秒 400+ 心跳、任务流无阻塞；
5. 前端首屏与大数据列表性能达标，支持千级任务/节点页。

## 2. IO 运行时升级（核心）

### 2.1 引入 compio（io_uring + IOCP）

- 候选运行时：**compio 0.19.2**（thread-per-core，Linux io_uring / Windows IOCP / 其他平台 poll；P3.1 已实测选定）；
- 备选：completeio（compio fork，偏 io_uring API）、lio（IOCP 未完成，暂不选）、tpt-torus（太年轻，观察）；
- 一期已确认：当前 tokio + 同步 std::fs；三期 P3.1 基准完成，结论：compio 顺序读比 tokio 高 10%~14%，与同步 std 差距约 7%，**P3.2 起块库迁移 compio**。

### 2.2 迁移路径

| 阶段 | 内容 |
| --- | --- |
| 3.1 评估与压测 | ✅ 已完成：256MiB 基准，std/tokio/compio/BLAKE3，见 [14-三期性能基准报告.md](14-三期性能基准报告.md) |
| 3.2 块库改造 | ✅ P3.2a 已落地：pread/pwrite、句柄复用、64 块批量索引提交；
   P3.2b 将 pack 读/写迁移 compio 异步文件 IO（排期中） |
| 3.3 数据面改造 | iroh 自定义 ALPN 的消息收发改为 compio 兼容异步流；块数据零拷贝（io_uring 提供 buffer 注册） |
| 3.4 网吧合并改造 | ✅ P3.4a 已落地：旧文件/复用源句柄复用 + 偏移读；
   P3.4b 迁移 compio/IOCP 异步化（排期中） |
| 3.5 双端一致性 | P3.5b：Windows 用 IOCP 走同一 crate 抽象，禁止按平台分叉业务代码（排期中） |

### 2.3 关键优化点

- **io_uring 固定缓冲（registered buffers）**：块读写复用固定 buffer，减少内存分配与拷贝；
- **SQPOLL 模式评估**：原始节点/IDC 高吞吐场景开启内核轮询提交队列，降低 syscall；
- **IOCP 对齐**：Windows 侧使用 overlapped IO + 完成端口，块库与数据面共用完成回调；
- **批量提交**：上传流按 16/64 块批量 append，redb 索引批量写，减少 fsync 次数；
- **大块 IO**：pack 顺序读写用 1MiB 对齐块；压缩时流式复制而非整文件载入；
- **异步哈希**：BLAKE3 多线程哈希与 IO 流水线重叠，磁盘等待期间算下一块。

## 3. 磁盘与存储优化

| 优化 | 说明 | 收益 |
| --- | --- | --- |
| pack 分片文件 | 单 pack 过大时按 8GB 分片，降低损坏面与压缩代价 | 200GB 单游戏可管理 |
| 写放大控制 | 延迟压缩只针对垃圾块区间重写，不做全量 | 减少 IO |
| 预分配 | 上传前按版本预估大小预分配 pack，避免碎片 | 顺序写 |
| 索引批处理 | redb 写事务按批合并，读事务短生命周期 | 吞吐提升 |
| 缓存分层 | 热块内存缓存（LRU）+ 冷块磁盘；网吧热文件内存映射 | 命中率提升 |
| 校验流水线 | 块哈希校验与写入并行 | 消除校验等待 |

## 4. 网络与数据面优化

| 优化 | 说明 |
| --- | --- |
| 批量块协议 | 单连接一次请求 N 块，服务端流式返回，减少每块 RTT（一期已批量，三期优化窗口/并发） |
| 多连接并发 | 按块并发控制连接数（4~16），多 IP 分流 |
| 零拷贝转发 | 兜底中继用 splice/io_uring，不经过用户态 buffer |
| QUIC 参数调优 | 初始窗口、最大流数、ACK 延迟按带宽调参 |
| 带宽调度 | 三期把二期限速做成数据面主动整形，避免 TCP 缓冲膨胀 |
| 压缩卸载 | 块级压缩可下放到专用核/io_uring，解压流式 |

## 5. 控制面优化

- 心跳/任务流消息批处理与压缩；
- 块账本内存索引 + 异步落盘，避免每块一次 redb 写；
- 任务调度器独立线程池，与 gRPC 服务解耦；
- 万级节点压测目标：注册 1w 节点 <30s，心跳 400 QPS 稳定，任务广播 <1s；
  ✅ P3.6a 已实测：直调注册 845 节点/秒、心跳 1481 次/秒，gRPC 注册 587 节点/秒、
  心跳 886 次/秒（见 [15-三期落地与压测报告.md](15-三期落地与压测报告.md)）；
  P3.6b 真实公网万级压测排期。
- 调度中心迁移 compio 仅限高 IO 路径，控制面保持 tokio（生态成熟）。

## 6. 前端性能

- 代码分割：antd 按需加载，首屏 JS 从 1MB 降到 400KB 内；
- 虚拟列表：千级节点/任务/审计列表；
- WebSocket 增量推送 + 本地缓存，避免全量轮询；
- 指标大盘用 Canvas/轻量图表，避免 DOM 卡顿。

## 7. 压测与验收指标

| 场景 | 目标 |
| --- | --- |
| 原始节点 1 万块顺序读（1MiB） | ≥ 2GB/s（NVMe + io_uring） |
| IDC 公网单连接吞吐 | 带宽 90% |
| 网吧合并 50GB 游戏 | 磁盘吞吐 ≥ 800MB/s，内存峰值 < 2GB |
| 1000 网吧并发拉取同一游戏 | 调度中心任务下发 < 1s |
| Windows 网吧（IOCP） | 与 Linux 同用例通过、无平台分叉 |
| 上传 4MB 大块 | 不再受消息上限影响（已 16MiB，三期做流式分片传输） |

## 8. 风险与回退

| 风险 | 应对 |
| --- | --- |
| compio 生态不成熟 | 只替换块库与数据面 IO 层，控制面保留 tokio；抽象 trait 隔离 |
| io_uring 内核版本要求 | 检测内核 ≥5.19，不满足自动回退 poll/同步 IO |
| IOCP 行为差异 | 统一抽象层做语义对齐，双平台跑同一套集成测试 |
| iroh 与 compio 集成困难 | 数据面保留 iroh QUIC，仅块读写替换；必要时自研 QUIC 适配层 |

## 9. 三期排期

P3.1 compio 评估与基准 → P3.2 块库异步化 → P3.3 数据面零拷贝 → P3.4 网吧合并异步化 → P3.5 控制面/前端性能 → P3.6 万级压测与上线。
