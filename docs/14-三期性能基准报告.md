# BlazeNet 三期性能基准报告（P3.1 compio 评估）

> 日期：2026-08-27
> 工具：`crates/blaze-bench`（release 构建，随 Linux 交付物一并产出）
> 目的：对比 std 同步、tokio 异步与 compio（io_uring）顺序读吞吐，为三期块库异步化选型提供实测依据。

## 1. 测试环境

| 项目 | 值 |
| --- | --- |
| 系统 | WSL2（Debian），内核 6.18.33.2-microsoft-standard-WSL2 |
| CPU/内存 | 12 核 / 30 GiB |
| 存储 | `/tmp`（tmpfs，内存盘） |
| 测试文件 | 256 MiB 确定性伪随机内容，写入 1245 MiB/s |
| 运行时 | compio 0.19.2（最新稳定版，默认 io_uring + runtime）、tokio 1.x |

> 说明：tmpfs 为内存盘，数据全量驻留页缓存，本报告衡量的是**各实现本身的 IO 开销差异**；
> 真实 NVMe/机械盘的绝对吞吐将叠加介质性能，计划在 P3.6 上线压测时按生产机型复测。

## 2. 实测结果（MiB/s）

| 实现 | 1 MiB 块 | 8 MiB 块 |
| --- | ---: | ---: |
| std BufReader（同步） | 3967.6 | 4372.2 |
| compio io_uring（按偏移 read_exact_at） | 3698.2 | 4102.0 |
| tokio fs（顺序 read） | 3365.9 | 3598.2 |
| BLAKE3 内存哈希（参考） | 7714.6 | 8147.9 |

明细：

```text
实现            块大小  耗时      吞吐
std BufReader        1MiB  64.522mss      3967.6 MiB/s
std BufReader        8MiB  58.552mss      4372.2 MiB/s
tokio fs             1MiB  76.056mss      3365.9 MiB/s
tokio fs             8MiB  71.147mss      3598.2 MiB/s
compio io_uring      1MiB  69.223mss      3698.2 MiB/s
compio io_uring      8MiB  62.408mss      4102.0 MiB/s
BLAKE3 内存哈希          1MiB  16.592mss      7714.6 MiB/s
BLAKE3 内存哈希          8MiB  125.677mss      8147.9 MiB/s
```

## 3. 结论与决策

1. **compio 可行且优于 tokio**：1 MiB 块场景 compio 比 tokio 高 9.9%，8 MiB 块场景高 14.0%；
   与同步 std 的差距收窄到 6%~7%（tokio 则落后 17%~18%）。
2. **io_uring 收益体现**：compio 使用内核完成队列，减少每次 read 的 poll 唤醒与用户态拷贝；
   块大小越大差距越明显，符合块库 1 MiB 块、上传 8 MiB 大块的既有设计。
3. **BLAKE3 不是瓶颈**：哈希吞吐 7.7~8.1 GiB/s，约为顺序读的 2 倍，支持三期"IO 与哈希流水线重叠"方案，
   校验等待不会成为数据面瓶颈。
4. **选型落地**：三期 P3.2 块库（pack 读写、临时块落盘）迁移到 compio；
   控制面（调度中心 gRPC/HTTP、心跳）保留 tokio，生态成熟且非 IO 密集。
5. **边界说明**：本基准不涉及 Windows；IOCP 路径在 P3.5 双端一致性阶段以同一抽象层覆盖，
   Windows 网吧端由用户后续明确要求后做系统服务集成。

## 4. 复现方式

```bash
cargo build --release -p blaze-bench
./target/release/blaze-bench 256            # 默认 256 MiB，临时目录
./target/release/blaze-bench 1024 /tmp/x   # 指定大小与文件路径
```

交付物：`bin/linux/blaze-bench`（CI/Release 自动构建收集）。
